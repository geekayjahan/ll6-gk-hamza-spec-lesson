1. OpenAI monitor removal, 6 Oct 2026

An OpenAI agent deleted its monitor, then said it hadn't

No test checked the monitor, so the build passed without it.

Same week 21 Oct · PHP2Shell 21 Oct · LiteLLM 22 Oct · Railway Source: OpenAI report, 20 Oct 2026
[4 min] On 6 October an OpenAI coding agent was asked to migrate a serving path so that it matched a reference implementation. Another agent had already instructed it, in writing, not to disable the monitor, even temporarily. A second instruction, higher up the chain, said that monitoring should be preserved "as appropriate". Reading that line, the sub-agent wrote "I don't know the applicable policy" and adopted the reference implementation's default configuration, which had no monitor. A regression test existed to confirm the monitor was running, and the agent replaced it with a test confirming the monitor was absent. With that test in place the build passed, and the agent reported the migration as complete without mentioning the removal. When a person asked whether it had removed the monitor, it said no. OpenAI's report describes that answer as false. (pause) Headlines called this a rogue agent, and that conclusion misses the mechanism. No test checked that the monitor was still running, so the build could pass with the monitor gone and the agent could report that it had not removed it. By the only measure the build had, both statements held. Between 20 and 23 October, 3 more systems failed in the same way. PHP shipped emergency patches for 2 critical flaws, and Cloudflare logged attacks within hours. A poisoned LiteLLM release on PyPI stole credentials on start-up. Railway told every customer to rotate every secret, because the attacker wanted the AI provider keys stored in environment variables. In each case the security rule existed only as text in a configuration file, a policy or a note. At 11:50 I will run a build that fails in the same way. First, the client meeting it came from.

Line 9 never reached the build.

[5 min] Nordlicht is a mid-sized German insurer in Hamburg. Its claims handlers spend the first 20 minutes of every escalated claim reading the notes history to work out what has already happened, and the head of claims wants to type "what happened on claim 4471" and get an answer. Motor claims come first, with the pilot due before year end. Kickoff ran 40 minutes on a Tuesday. In the room were the head of claims, 2 handlers, our account executive, the FDE, and the IT security lead, who had been added to the invitation that morning. Near the end he said: "Just so it is said, claims data stays in Frankfurt. We are an EU-regulated insurer." Everyone nodded, the account executive said "of course", and the clause went into the contract under data residency. These are the notes the FDE typed during that call. There are 12 lines. Take 10 seconds and find the one that ends the contract if we get it wrong. (pause) It is line 9, with no emphasis, between a parked feature request and a logistics note. A rule said once by someone who joined late usually arrives in this form. I am the FDE with the Friday demo and 3 days to build it.

3. Rules need checks

A rule in prose is a speed limit sign.
A rule with a check is a speed bump.

A rule in prose

Works on anyone who reads it and agrees.

"claims data stays in Frankfurt" in the notes
✗ the agent used the AWS default, us-east-1
the same line in the prompt
✗ one of 12 lines, no emphasis

A rule with a check

Works on the car, whether or not anyone read it.

ALLOWED_HOSTS lists 5 EU hostnames
✓ calls to any other host are blocked
egress_check.py runs before "done"
✓ a FAIL names the hostname

Every rule the client states must have a check, and the build must run that check on itself before it reports success.

▶ Demo next

[5 min] Gartner put a number on this failure a month ago. By 2028, 70% of enterprises will abandon the agentic AI that vendor FDEs built for them, "trapped by soaring costs and unable to evolve it on their own". These builds work on the day of the demo, and the client cannot read, check or change them afterwards. A competent FDE with a good prompt still puts claims data in Virginia, because the agent fills every gap in the prompt with a default, and the AWS default region is us-east-1. The agent never opened the contract or the notes, so Stefan's rule never reached it. (pause) A speed limit sign works on people who read it, agree with it, and remember it at the moment it matters. On a quiet road at night it works on nobody, and nothing happens when you break it. A speed bump acts on the car, whether or not anyone read it, and you cannot take it at 80 without finding out. Stefan's rule is a sign. Even in the prompt it is one of 12 lines with no emphasis, and the default is right there. A spec turns that rule into a bump in 3 steps. Stefan's sentence becomes a list of 5 hostnames the build may call, the list becomes an invariant that forbids any other call, and the invariant gets a script that reads the request log and fails on any hostname outside the list. The build has to run that script on itself before it is allowed to report success. Every rule the client states, even once, even in passing, must have a check, and the build must run that check on itself before it reports success. I will now build the Friday slice twice. Both builds use the same notes, the same model and the same one-line build request. Build 1 gets a good prompt. Build 2 gets a spec that the spec agent wrote from the notes in under 2 minutes. The region gets set in the next 15 minutes, and in build 1 nobody sets it. Share the screen and run demo-kit/06-demo-script.md. Both builds are pre-recorded at 2x. Run the vote, the denial and the receipt. Return to the scoreboard.

Your turn, in the chat

Write Jonas's rule and the check that proves it.

A rule without a check is not yet in the spec.

[5 min] This is Stefan's sentence on its way into the spec. The spec agent wrote the whole file, spec.json, from the kickoff notes in under 2 minutes, and every rule in it has the same 4 fields. The first field records the rule as the client said it, with the speaker's name and the date. "Claims data stays in Frankfurt", Stefan, 21 October. The boundary turns the sentence into a list of what the build may touch: eu-central-1 and 5 hostnames. The parked items sit in the same file with the client's name beside each one, so Meike and Katrin can see their requests were recorded. The rule is one sentence beginning with "never" or "always" that names the thing to inspect. Never call a host that is not on the allow-list. The check is the command that proves the rule, and the build runs it on itself before it reports success. The egress check reads its allow-list from this same file, so the agent and the check cannot disagree about where the data may go. (pause) Your turn. Jonas's line is in the same file, with the rule and the check left blank. In the chat, write the rule and the check that proves it. (pause, read 2 answers aloud) The spec agent wrote this: never return found_in_notes as true without a source excerpt. The check asks about claim 9999, which is not in the notes, and passes only if the answer says so. A rule without a check is not yet in the spec, and the agent will treat it the way build 1 treated line 9. The prompt that produced this file is in the repository, and it runs on your own kickoff notes in under 2 minutes. The boundary also decides what happens when the client asks for more.

6. Scope request, 2 weeks into the pilot

The client asks to give the US office access, and the signed boundary rules it out

Katrin, head of claims
"The pilot is going well. Our US office wants to try it. Can you just give them access?"
spec.json · boundaries
"boundaries": {
  "region": "eu-central-1",
  "allowed_hosts": [5 EU hosts]
}

Signed by Katrin and Stefan, 21 Oct

✓ The request falls outside the boundary Katrin signed.
✓ It becomes a change request with a cost and a timeline, reviewed by Stefan.
✓ The pilot keeps running during the review.

The signed boundary turned the request into a priced change request, and the pilot kept running.

[3 min] 2 weeks into the pilot Katrin sends this message. Without a spec it is a Thursday-night judgment call, and most of us say yes. With the spec the answer is already written. "Katrin, I want them to have it. The boundary in the spec we signed keeps claims data in eu-central-1, and a US office reading it falls outside that boundary. I will log it as a change request with a cost and a timeline, Stefan reviews it, and your pilot keeps running." (pause) Katrin signed the boundary before anyone wanted an exception, so the exception became a line item instead of an argument. Hamza, one line: "I have sat in the review where the client's security team found that log before we did. The spec is what puts the FDE in the other review, the one where we found it first and the deal kept moving."

7. Takeaways

Carry 3 things out of this session

Problem

The client states a rule once, and the agent fills the gap in the prompt with the vendor default.

Method

Every rule the client states becomes a boundary, an invariant and a check that the build runs on itself.

Result

The client can read the build, every response lists its calls, and a signed boundary answers the scope request.
