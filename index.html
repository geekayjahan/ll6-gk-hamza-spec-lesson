3. Rules need checks

A rule in prose is a speed limit sign.
A rule with a check is a speed bump.

A rule in prose

Works on anyone who reads it and agrees.

"claims data stays in Frankfurt" in the notes
✗ the agent used the AWS default, us-east-1
the same line in the prompt
✗ one of 12 lines, no emphasis

A rule with a check

Works on the car, whether or not anyone read it.

ALLOWED_HOSTS lists 5 EU hostnames
✓ calls to any other host are blocked
egress_check.py runs before "done"
✓ a FAIL names the hostname

Every rule the client states must have a check, and the build must run that check on itself before it reports success.

So what's inside the spec? Let's zoom in.

The spec-based approach

Every spec has the same six parts, whatever the client asks for

Written before the build

You fill in all six parts from the client's own words at kickoff, before the agent writes any code.

Every part can be checked

Each fuzzy word ends up as a pass or fail test in part 6, so the client, the FDE and the agent grade the build the same way.

Reused on every engagement

The next client gets the same skeleton. Only what goes inside each part changes.

A prompt asks for an output. A spec also sets the limits and the test.

[2 min]

Before we zoom into Stefan's rule, here's the shape every spec takes.

  • 6 parts, same order on every build:
    1. Problem → who has it, what breaks today. No solution yet
    2. What good looks like → the behaviour in one pass
    3. Inputs & interfaces → the data, files and systems it may touch
    4. Non-goals → what it won't do. You'll need this when the client asks for more
    5. Task decomposition → ordered steps, each with a done-check
    6. Verification → pass/fail tests 2 graders would score the same

(pause)

So what does spec-based mean?

  • You fill these in before the agent writes a line
  • From the client's words, at kickoff
  • Every fuzzy word becomes a test in part 6
  • Next client → same skeleton, new contents

7. Takeaways

Carry 3 things out of this session

Problem

The client states a rule once, and the agent fills the gap in the prompt with the vendor default.

Method

Every rule the client states becomes a boundary, an invariant and a check that the build runs on itself.

Result

The client can read the build, every response lists its calls, and a signed boundary answers the scope request.
